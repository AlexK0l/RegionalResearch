# RegionalResearch

Веб-приложение для регионального поиска потенциальных покупателей CAT.

## Как работает

Интерфейс оставлен только для рабочего сценария: запуск полного исследования, продолжение с checkpoint, остановка, скачивание checkpoint и итогового XLSX. Smoke/quality/stage/replay-кнопки из пользовательского UI удалены; диагностические режимы остаются внутренними возможностями backend/test-кода.

1. Пользователь выбирает регион.
2. Шаги 1–9 выполняют последовательный поиск через OpenAI Responses API с web_search.
3. После discovery выполняется отдельный Entity Census / coverage-pass по ключевым секторам и географическим пробелам.
4. Шаг 10 детерминированно объединяет результаты, выполняет qualification, повторную проверку ИНН, post-INN dedupe, параллельное точечное enrichment и региональную статистику.
5. Шаг 11 сначала ищет контакты обычным web_search для каждой компании, проверяет конфликтующие телефоны по ИНН и только для оставшихся A/B использует Google AI Mode как ограниченный fallback.
6. После завершения формируется итоговый XLSX.

## Структура

- `server.js` — Express Web Service и API заданий.
- `src/fileLogger.js` — маршрутизация console-логов в отдельный файл каждого research job.
- `src/checkpointStore.js` — SQLite-хранилище checkpoint.
- `src/` — исследовательский pipeline, Google AI Mode и генерация XLSX.
- `prompts/` — инструкции шагов 1–10.
- `public/` — пользовательский интерфейс.
- `render.yaml` — конфигурация Render.

## Локальный запуск

Локальный режим не требует Redis, Postgres или отдельного хранилища. Checkpoint сохраняется в SQLite на диске, а каждый запуск исследования получает отдельный файл лога.

1. Установите Node.js 22 или новее.
2. Установите зависимости и Chromium:

```bash
npm install
npm run browser:install
```

3. Создайте локальный `.env` из примера.

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

macOS / Linux:

```bash
cp .env.example .env
```

4. В `.env` укажите как минимум:

```env
OPENAI_API_KEY=ваш_ключ
CHECKPOINT_DB_PATH=./data/checkpoints.sqlite
LOG_DIR=./logs
```

5. Запустите приложение:

```bash
npm run local
```

После запуска откройте `http://localhost:10000`. UI и API работают с одного локального процесса, поэтому отдельный frontend-сервер не нужен.

Локальные данные:

- SQLite checkpoint: `data/checkpoints.sqlite`;
- WAL-файлы SQLite: рядом с основной БД;
- общий серверный лог: `logs/server-YYYY-MM-DD.log`;
- отдельный подробный лог каждого исследования: `logs/jobs/<timestamp>_<region>_<job-id>.log`.

Каталоги `data/`, `logs/` и файл `.env` исключены из Git. После остановки и повторного запуска приложения checkpoint остаётся на диске и доступен через обычную кнопку продолжения исследования.

По умолчанию приложение слушает `PORT` или порт `10000`. Пути можно изменить через `CHECKPOINT_DB_PATH` и `LOG_DIR`.

## Render

Основная ветка: `main`.

Render продолжает использовать переменные окружения сервиса. Локальный `.env` на Render не нужен. Для free-инстанса текущий путь checkpoint остаётся `/tmp/regionalresearch/checkpoints.sqlite`; локально используется постоянный файл `./data/checkpoints.sqlite`.

Build command:

```bash
npm install && npx playwright install chromium
```

Start command:

```bash
node server.js
```

Переменные окружения:

Шаги 1–9 ограничиваются 50 000 output tokens и сохраняют скрытый evidence (URL, официальный сайт, email и найденные подтверждения). После них Entity Census отдельно проверяет полноту состава действующих организаций по перевозчикам, агро/зерну, карьерам, стройматериалам, лесу, отходам/лому и крупным промышленным грузовладельцам; затем выполняются только ограниченные coverage-gap проходы по недопокрытым сектору и географии.

Шаг 10 больше не прогоняет весь canonical-пул через массовые LLM-batch. Базовые строки строятся детерминированно; модель используется только для неоднозначных конфликтов. Финальная проверка ИНН выполняется параллельными батчами, затем обязательно повторяется dedupe. Если одинаковый ИНН остаётся у несовместимых сущностей после конфликтной перепроверки, такой ИНН очищается до однозначного подтверждения, а сами релевантные строки не удаляются. Обычный enrichment не имеет права менять ИНН, телефон или ЛПР; он параллельно заполняет только оставшиеся поля компании и переиспользует уже собранный evidence. Региональная статистика собирается параллельно. Checkpoint записывается пакетно, а не после каждой компании.

Шаг 11 является web-first. Для каждой строки с незаполненным телефоном или ЛПР выполняется поиск по названию + ИНН + «контакты»; при отсутствии телефона допускается второй запрос название + ИНН + «телефон». Если один номер встречается у разных компаний, он отдельно проверяется запросом телефон + ИНН. Google AI Mode через Playwright запускается только как fallback для оставшихся A/B, максимум в двух параллельных сессиях и по умолчанию с двумя computer-use ходами. Автоматический полный Luna → Sol повтор отключён; CAPTCHA, отсутствие AI Mode и высокий процент unavailable открывают circuit breaker. Этапы 10 и 11 имеют целевой wall-time budget 28 минут каждый.

Одновременно выполняется не более одного полного исследования; диагностические режимы очередью полного исследования не блокируются.


### Полнота этапов 1–9

Этапы больше не выполняются тремя общими проходами. Каждый этап имеет обязательный набор тематических поисковых веток, сформированный из исходных пользовательских инструкций. Каждая ветка делает серию web-search запросов по своей теме, проходит географию региона и передаёт следующей ветке список уже найденных организаций, чтобы искать long tail вместо повторов.

Recovery внутри этапов ограничен и служит страховкой, а не вторым полным обходом. Основной контроль полноты выполняет Entity Census после этапов 1–9: система считает coverage по ключевым секторам и локальным географическим группам, а затем делает ограниченный gap-search только по явно недопокрытым сочетаниям. Это не квота: выдумывать компании ради количества запрещено.

A/B/C не используется как фильтр допуска на discovery. В частности, коммерческий грузовладелец с подтверждённым действующим целевым производственным/грузовым процессом может сохраниться как C, даже если собственная техника или перевозчик ещё не установлены. Органы власти и бюджетные учреждения исключаются из коммерческих листов; ГУП/МУП/ФГУП оцениваются по фактической хозяйственной роли.

Шаг 10 не компенсирует слабый discovery массовым поиском. Возможные дубли без ИНН объединяются консервативно; после обязательной повторной проверки ИНН выполняется ещё один deterministic dedupe. Отсутствие подтверждённого ИНН само по себе не удаляет релевантную организацию.


### Судебный архив для этапа 7

В проект встроен компактный индекс пользовательского архива из 10 109 markdown-документов судебных актов. Индекс содержит названия судов и организаций, упомянутых в документах, и используется только на этапе 7 как дополнительный источник discovery по выбранному региону. Найденные по архиву организации затем проверяются через web_search/официальные судебные источники; одно упоминание в архиве не считается достаточным доказательством владения или эксплуатации техники.


### Формат итогового XLSX

Исследовательский pipeline продолжает работать с 12 смысловыми полями, чтобы не расходовать поисковый бюджет на CRM-служебные колонки. При экспорте данные раскладываются в эталонный формат: «Прямые покупатели» — 37 колонок, «Посредники» — 26, «Лизинг» — 27. Дополнительно создаются листы «Статистика» (6 содержательных колонок), «Статистика по цветам» и «Легенда». Выручка и численность записываются только числовыми значениями.

### Регрессионное сравнение с эталоном

Эталон не используется в production-discovery и не передаётся модели как список компаний. Для внешнего frozen benchmark доступна команда:

```bash
npm run benchmark:reference -- current.xlsx reference.xlsx
```

Она считает exact-INN/name recall, дубли подтверждённых ИНН, попадание органов власти/бюджетных учреждений и покрытие телефонами/ЛПР/выручкой/численностью. TORGBOX в расчёт recall не входит. При необходимости CI-порог можно задать через `BENCHMARK_MIN_INN_RECALL`, `BENCHMARK_MIN_NAME_RECALL`, `BENCHMARK_MAX_DUPLICATE_INN` и `BENCHMARK_MAX_GOVERNMENT`.


## Evidence-first оптимизации (экспериментальная ветка)

Результат финальной квалификации формирует коммерческие действия из уже собранного evidence без дополнительных web-поисков. B требует независимых семантических сигналов в evidence. Структурные факты `__evidence.facts` с `source_url`, `fact_type` и `statement` поддерживаются дополнительными функциями качества; для прежних снимков используется совместимый анализ заметок. Текущий discovery-поиск не меняет широту этапов 1–9.

Повторная проверка ИНН может завершаться локально для записей, у которых есть `__evidence.identity_verification` с совпадающим ИНН и URL источника; старые записи без такой метки по-прежнему проходят web-проверку. Это консервативный механизм, который ещё требует сравнения на replay-снимке.

Переменная `OPENAI_FULL_WEB_MAX_CALLS` задаёт предельное число вызовов web_search полного запуска (по умолчанию 4500). Превышение останавливает новый web-запрос; это предохранитель, а не гарантия полной денежной стоимости. Денежная стоимость зависит также от токенов и тарификации.

Локальный запуск `npm run local` работает без `API_ACCESS_TOKEN`: для доступа только с собственного ПК этот параметр необязателен. При публикации сервиса в сеть можно задать `API_ACCESS_TOKEN` в локальном `.env` или в настройках той среды, где реально запущен backend. Интерфейс запросит токен и сохранит его в sessionStorage браузера. **Не записывайте токен и ключ OpenAI в Git.**

Все изменения требуют проверки через GitHub Actions и контрольный replay перед merge в main.

Пакетное обогащение управляется `OPENAI_ENRICHMENT_BATCH_SIZE` (1–5, по умолчанию 3). Для всего пакета установлено ограничение `OPENAI_ENRICHMENT_BATCH_MAX_TOOL_CALLS` (по умолчанию 2). **Пустые поля при корректно возвращённой строке больше не запускают платный повторный поиск**: отсутствие достоверных сведений само по себе не ошибка. Только пропуск или повреждение строки допускает ограниченный fallback для A/B — не более `OPENAI_ENRICHMENT_MAX_FALLBACKS_PER_BATCH` (1) на пакет и `OPENAI_ENRICHMENT_MAX_FALLBACKS_TOTAL` (40) на исследование. Эти лимиты регулируют вызовы, но не гарантируют точную стоимость биллинга. `OPENAI_MAX_RESEARCH_COST_USD` (60 по умолчанию) — расчётный предохранитель с настраиваемыми токеновыми тарифами `OPENAI_ESTIMATE_*`; реальный биллинг может отличаться. Browser fallback теперь включается только через `GOOGLE_AI_FALLBACK_ENABLED=true` после подтверждения его работоспособности.

Кэш контактов прошлых запусков (`OPENAI_PREVIOUS_CONTACT_CACHE=true`) читает только завершённые checkpoint того же региона. Телефон может повторно использоваться не более 90 дней при совпадении контрольного ИНН и наличии URL, сохранённого после поиска контакта. Эталонные файлы в discovery и кэш не поступают. При локальном запуске SQLite хранится в `./data/checkpoints.sqlite` и остаётся на диске ПК после перезапуска Node; не удаляйте каталог `data/` при обновлении проекта.

### Контрольный запуск оптимизированной версии на локальном Windows ПК

Основная среда работы — **локальные Node.js, SQLite и браузер**, а не Render. В PowerShell, находясь в существующей папке проекта, и убедившись, что нет незакоммиченных изменений:

```powershell
git fetch origin
git switch --track origin/feature/evidence-first-cost-quality-20261028
npm install
npm run local
```

Открыть `http://localhost:10000`. Существующий `.env` с `OPENAI_API_KEY`, а также `data/` и `logs/` не должны удаляться при переключении ветки. Чекпоинты хранятся в `./data/checkpoints.sqlite`, логи — в `./logs/jobs/`. Переменные лимита затрат при необходимости меняются **в локальном `.env`**, например `OPENAI_MAX_RESEARCH_COST_USD=35`. Это оценочный программный порог, а не точный лимит OpenAI Billing. Новая ветка остаётся экспериментальной до контрольного прогона; `main` не меняется.

### Диагностика сохранённого исследования без API

Запущенный локально проект поддерживает анализ существующих журналов и Excel без обращения к OpenAI:

```powershell
npm run replay:qualification -- "logs/jobs/ИМЯ_ФАЙЛА.log" "SAT_Смоленская_область.xlsx"
```

Команда показывает фактическую структуру поисковых расходов в логе, количество пакетных и одиночных обогащений и проверяет, какие **доступные в диагностическом логе** доказательства допускают класс B. Список компаний B/C в отчёте — **кандидаты на проверку**, а не автоматическое решение: логи содержат выборки discovery, не полный набор финальных объединённых свидетельств. Для полной перепроверки квалификации нужен сохранённый checkpoint. Экспортёр и production-discovery не используют эталон v4. Действительный эффект новых лимитов можно будет измерить только последующим контрольным запуском.

### Контроль дублей юрлиц и спорных ИНН (локально)

После финальной проверки ИНН программа сначала проверяет совместимость подтверждённых юридических названий, исторических наименований и сокращений. Для неочевидных алиасов требуются индивидуальные подтверждения ИНН и общие проверочные URL либо явное подтверждение переименования. **Одинаковый ИНН без достаточных доказательств не считается достаточным основанием для объединения**. Разные ОГРН, несколько противоречащих ОГРН в одной записи и разные юридические роли (филиал / юридическое лицо, группа / организация) запрещают автоматическое объединение.

Безопасные объединения сохраняются в `__evidence.legal_identity_merges`: старое/новое наименование, основание решения, ИНН, ОГРН и адреса источников. Конфликты, которые остались после перепроверки, сохраняются как `__evidence.legal_identity_conflicts`; организация НЕ удаляется, но спорный ИНН очищается и требует ручной проверки. Ссылки на сторонние справочники и LLM-заметки являются указателями на источник, а не гарантией его достоверности.

Для **бесплатной** диагностики уже сохранённого контрольного запуска откройте PowerShell в каталоге проекта и выполните:

```powershell
npm run replay:identity -- "data/checkpoints.sqlite"
```

Команда читает последний завершённый `full` checkpoint, оценивает возможные объединения на основании сохранённых подтверждений и печатает JSON: `potential_alias_merges`, `groups_still_requiring_review`, причины по каждой спорной группе. База SQLite и WAL не изменяются. **Команда не возвращает очищенные в старом запуске ИНН и не изменяет его Excel.** Исправление применяется к следующим исследованиям либо к отдельному контролируемому переобрабатыванию исходных записей. Не удаляйте и не заменяйте исходную базу перед проверкой.

Для внесения изменений в рабочую базу недостаточно одного эвристического совпадения: все неоднозначные алиасы и противоречащие ОГРН должны быть подтверждены по первичному реестру или документу соответствующего юрлица.

### Восстановление ИНН и объединение алиасов в отдельной копии (без API)

Для ранее завершённого исследования в локальном SQLite сначала можно сделать read-only диагностику (`npm run replay:identity`), а затем создать **производную копию** с подтверждёнными алиасами, не изменяя ни SQLite с WAL, ни исходный Excel:

```powershell
npm run recover:identity -- "data/checkpoints.sqlite" "--out=exports/offline-smolensk-recovered"
```

Для сохранения **всех исходных рабочих колонок SAT**, незатронутых вкладок и вручную заполненных CRM-полей используйте исходную выгрузку через `--template`. Система строго проверяет, что порядок и названия исходных строк Excel совпадают с исходным checkpoint; при расхождении прекращает экспорт, чтобы не переносить заметки между компаниями. После слияния уникальные CRM-значения алиасов сохраняются, противоречия выносятся в отдельный лист. Визуальная точность стилей и макросов библиотекой SheetJS не гарантируется:

```powershell
npm run recover:identity -- "data/checkpoints.sqlite" "--out=exports/offline-smolensk-recovered" "--template=D:\\RegionalResearch\\SAT_Смоленская_область.xlsx"
```

Создаются **три новых файла**: `identity_recovery_<id>_result.xlsx`, `identity_recovery_<id>_result.json` (все сохранённые заметки/URL) и `identity_recovery_<id>_audit.json` (объединения, подразделения, конфликтные значения, отложенные проверки). Если выходные файлы уже существуют, скрипт завершится с ошибкой — выбрать новую папку `--out`, **не перезаписывать первичные данные**.

Без `--template` выгружается упрощённый **13-колоночный обзор**, а не полноценный CRM-файл. В обоих режимах ИНН в текстовом `__comment` синхронизируется с новым значением. Если исходные алиасы имели разные классы A/B/C, выбранный исходный класс **не повышается автоматически**; расхождение фиксируется в `qualification_conflicts` и на отдельном листе «Проверка A-B-C». Такой лид следует пересмотреть по первичным документам.

Алгоритм восстанавливает спорный ИНН только при наличии двух отдельных checkpoint-записей с валидным ИНН, подтверждения `identity_web`/`final_inn_web` и HTTP(S)-источниками, прежней отметки финального конфликта и положительного решения попарной проверки алиасов. Противоречащие ОГРН, разные юридические роли, другое уже заполненное ИНН и одиночные спорные записи НЕ восстанавливаются. Если два названия относятся к одному юрлицу, сохраняются все ссылки и заметки, исходные имена и ID. Финансовые показатели разных строк НЕ суммируются, альтернативные значения выводятся в аудит; телефонные номера объединяются с сохранением исходных источников. Существующие категории A/B/C сохраняются без переквалификации.

Это **постобработка завершённого отчёта**, а не новое исследование и не доказательство актуальности каждого упомянутого источника. Команда не делает OpenAI вызовов и не восполняет непроверенные ИНН. Исходный `main`, SQLite, WAL и исходный Excel не меняются.

На контрольной базе Смоленской области от 28.10.2026 обнаружены 10 безопасных пар алиасов из 15 спорных ИНН: 540 исходных строк превращаются в 530, заполненных ИНН становится 429 вместо 419. Это локальная оценка на сохранённых доказательствах; новый полный контрольный запуск не проводился.
